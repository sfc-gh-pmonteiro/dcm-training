Foundations · 01

Core principles

Teams that do DevOps well on Snowflake agree on a few principles before they pick tools. The tools then follow from the principles, not the other way around.

1Everything in Git

Object definitions, migration scripts, transformation code, and app code all live in version control. Production gets nothing that didn't come through Git.

2Deploy only through CI/CD

Pipelines deploy with service users. Developers should touch production as little as possible.

3Automated execution

Pipelines run on schedules or events, such as new files landing or a stream having data. Nothing depends on a person remembering to click "run".

4Deterministic, convergent state

Every deployment moves an environment toward the same intended state. Dev, test, and prod differ only by configuration, not by hand-applied fixes.

5Validate before you deploy

Review a plan or dry run on every pull request. Look at creates, alters, and especially drops before you merge.

6Roll forward

When a deployment fails, ship a new forward change that fixes it. Hand-written undo scripts rarely work once data has changed.

7One owner per object

Exactly one tool manages each object. Two tools reconciling the same object will fight each other.

8Decide what you automate

Be explicit about what a central platform team provides and what each project team owns. That boundary drives tool choice more than features do.

No single tool covers everything. Real pipelines usually combine several mechanisms: one to manage object state, one for transformations (dbt), one for code-backed objects (Snowflake CLI), and something for account-level setup. That's normal. What matters is that each object has one clear owner and the pipeline runs the tools in a defined order.

Build an object-ownership map

Before choosing tools, list every object type you will manage and assign each one to exactly one owner. Do it on a whiteboard first, then keep the result in the repository as part of the project's documentation. Review it whenever a new object type or tool is added. An example:

Account-levelWarehouses, databases, resource monitors, integrations, network rules and policiesPlatform team (Terraform or DCM Projects)

Foundations · 02

The layers model

Most confusion about tools disappears once you split the platform into layers. Each layer changes at a different rate and usually has a different owner.
Account / environment
Accounts, warehouses, top-level databases, roles, integrations, network rules and policies. Changes rarely and is owned by the platform team. Typical tools: Terraform, DCM Projects, or parameterized scripts.
Database objects
Schemas, tables, views, stages, file formats, tasks, streams, dynamic tables, functions and procedures. Changes often and is owned by data engineering. Typical tools: DCM Projects, schemachange, Flyway, or Liquibase.
Transformation
Models that produce tables and views from source data. Typical tool: dbt, run either as dbt Projects on Snowflake or as self-hosted dbt Core.
Code-backed objects
dbt Projects, notebooks, Streamlit apps, Snowpark procedures and functions with packaged code, Snowpark Container Services, and code bundles. Typical tool: Snowflake CLI (snow), called directly or from a migration tool.
Ingestion
Getting data in: Snowpipe, Snowpipe Streaming, Openflow, COPY, and partner tools. Ingestion is separate from transformation. Neither dbt nor change-management tools load data.
Orchestration
When things run: Snowflake Tasks and task graphs (native), or an external orchestrator such as Airflow, Dagster, or Prefect when you need cross-system control.
Identity & access
Users and groups from your identity provider through SCIM, plus role hierarchies and grants. Usually a dedicated process with its own owner.

Foundations · 03

Declarative vs imperative

Change-management tools fall into two families. Both are valid, and they solve the problem from opposite directions.
Declarative (desired state)Imperative (migration scripts)
How it worksYou describe what objects should look like. The tool compares that with the account and works out the changes.You write ordered scripts with the exact changes. The tool runs each one once and records that it ran.
ExamplesDCM Projects, Terraformschemachange, Flyway, Liquibase (changelogs)
StrengthsOne readable definition per object. Plan and diff before deploy. Drift detection. Fewer files over time.Can express any change, including data fixes, backfills, renames, and multi-step table rebuilds. Full audit history.
Trade-offsLimited to what the tool can compare and ALTER. Renames and breaking changes need a separate step. Removing a definition can drop an object.No single file shows "current state". History grows over time. Script authors are responsible for idempotency.
Data changesNot the job of the definition files.First-class. A script can ALTER and then UPDATE.
Combining them. Many mature teams treat the two as complementary: a declarative definition for the shape of most objects, plus an imperative path for the changes it can't express, such as a backfill, a column type change that needs a rebuild, or a rename. If you combine them, give each object a clear owner and decide upfront which kinds of change take which path.

What declarative diffs can't express

A comparison tool sees only the before and after shape, not the intent. Moving data between structures needs an explicit, ordered script:

-- Move ownership from a column on ITEM to a new RELATIONSHIP table
CREATE TABLE relationship (
  item_id INT NOT NULL,
  user_id INT NOT NULL,
  type    VARCHAR NOT NULL
);

INSERT INTO relationship (item_id, user_id, type)
  SELECT id, owner_id, 'owner' FROM item;

ALTER TABLE item DROP COLUMN owner_id;

A declarative diff would create the new table and drop the column, and the ownership data would be lost. This is why declarative setups still need a tracked imperative path.

Organize the repository to match the approach

Declarative

Mirror the database: database/schema/<object type>/<object>.sql, one file per object, named after it. Browsing the repo feels like browsing the account.

Imperative

Don't copy the declarative folder tree. A migration script often changes several objects, so per-object folders cause confusion. Organize by release or version (for example migrations/v2/), and put the work-item or user-story ID in each file name, such as V2.3.0__STORY-1234_add_channel.sql, so every change traces back to a requirement.

How AI coding agents see "current state". With declarative files, the agent can read the definitions. With a long migration history, the most reliable source is the live account: INFORMATION_SCHEMA, SHOW, and GET_DDL, against a non-production environment. Either way, give agents the repo and read-only metadata access.

Tooling · 04

DCM Projects GA Aug 2026

DCM Projects is Snowflake's native declarative change-management feature. Snowflake's DevOps documentation describes it as the recommended Snowflake-native option for objects inside your databases, with Terraform for the account and external-infrastructure layer.

How it works

  • manifest.yml sets deployment targets (account, project object, owner role) and templating configurations for each environment.
  • Definition files under sources/definitions/ contain DEFINE, GRANT, and ATTACH statements, with Jinja2 for variables, loops, and macros.
  • PLAN, then DEPLOY. PLAN compares definitions with the account and lists creates, alters, and drops without changing anything. DEPLOY applies them. Each DEFINE runs as CREATE OR ALTER, so the CREATE OR ALTER limits for that object type apply.
  • You can run it from Snowsight, the Snowflake CLI (snow dcm plan / deploy), SQL (EXECUTE DCM PROJECT), or Cortex Code. Files can live in a Workspace, a Git repository, or a local directory.
-- sources/definitions/raw.sql
DEFINE SCHEMA {{db}}.RAW;

DEFINE FILE FORMAT {{db}}.RAW.CSV_FMT TYPE = CSV SKIP_HEADER = 1;

DEFINE TABLE {{db}}.RAW.ORDERS (
  ORDER_ID NUMBER, CUSTOMER_ID NUMBER, AMOUNT NUMBER(12,2), LOADED_AT TIMESTAMP_NTZ
);

GRANT SELECT ON TABLE {{db}}.RAW.ORDERS TO ROLE {{env}}_ANALYST;
# validate on pull request, deploy on merge
snow dcm plan   --target PROD
snow dcm deploy --target PROD

Supported objects

Coverage is broad and growing. It includes databases, schemas, tables, views, dynamic tables, tasks, stages, file formats, sequences, functions and procedures in all handler languages, alerts, semantic views, shares, tags, roles, warehouses, network rules, authentication and network policies, plus grants and data metric function attachments. Always check the supported entities page for the exact objects and properties you need.

Still in preview at GA (per the GA release note): TEST and PREVIEW commands, the GitHub Actions for DCM Projects, DEFINE PIPE, DEFINE STREAM, DEFINE MASKING POLICY, DEFINE ROW ACCESS POLICY, ATTACH TAG, inherited grants, and container-level MANAGE GRANTS. Streamlit and code bundle assets are also marked preview on the supported entities page.

Behaviors to understand before production

BehaviorWhat it means for you
Removing a DEFINEThe managed object is dropped on the next deploy. Make PR review of PLAN output, especially drops, a required gate.
Changes ALTER can't makeOnly changes CREATE OR ALTER supports can be deployed. Renames and some column changes are done outside DCM (for example with ALTER ... RENAME), then the definition is updated so the next PLAN shows no change.
Data fixes and backfillsNot part of definition files. Use a separate, tracked mechanism such as an imperative tool or a controlled job.
GrantsDCM manages the grants it deployed. Removing a GRANT from definitions revokes it. Grants created outside DCM coexist and aren't removed, so DCM doesn't by itself enforce "no extra privileges".
DriftA full PLAN against the last deployed definitions shows differences from the current account state.
RecoveryRedeploying an older definition reconciles object shape. It isn't a data rollback. Use Time Travel or clones for data.
Partial deploysDEPLOY recomputes the changeset at run time, rather than replaying a saved PLAN. A failure during the DDL step can leave some changes applied. Fix the cause and deploy again to reach the defined state.
Tasks and alertsNew tasks and alerts are deployed suspended. Add STARTED to the definition if they should run. A task defined as STARTED is started again on the next deploy, even if someone suspended it by hand.
Immutable propertiesSome properties can't be altered: a pipe's COPY body, most stream properties, and a network rule's TYPE and MODE. Changing them means dropping and recreating the object, so plan for that.

Structuring projects

A project folder holds manifest.yml and the definitions. Each target in the manifest maps to one DCM project object, with its own owner role and templating configuration. Snowflake's architecture guidance describes three shapes:

ShapeFits whenExample
A. One folder, one targetMost objects share an owner role. Loops generate a modest number of similar resources (Snowflake suggests about 20 iterations as a rule of thumb).One template creates the same database structure for each regional team.
B. One folder, many targetsDeployments share definitions but need different owner roles, or must deploy and fail independently.A platform team with 100+ tenants, one target per tenant. Each target can be deployed in parallel.
C. Separate foldersTeams maintain mostly different definitions, with few dependencies between them.A platform project provides databases, warehouses, and admin roles. Each domain team's project builds inside them.
  • Keep cross-project dependencies one-directional. DCM orders statements within one deployment but doesn't coordinate across projects. Deploy upstream projects first, and avoid cycles, such as two projects that each reference the other's objects.
  • Grants can live in their own project when a different team owns access. The trade-off is that the infrastructure project must deploy first. Without that organizational need, keeping grants next to the objects is simpler.

Environments and developers

  • Create one DCM project object for each environment. A project has only one deployed instance at a time. Deploying a different configuration to the same project drops anything that configuration doesn't define.
  • Template every account-level name (databases, warehouses, roles) so environments, and each developer, get distinct objects. Two projects can't manage the same object, so a developer's deploy fails if another developer's project already owns that name.
  • Give each developer or ticket a sandbox: a separate project object plus a unique name variable. Use PLAN DELTA for fast feedback while editing, a full PLAN before any deploy, and PURGE to remove the sandbox afterwards.
# manifest.yml (excerpt)
targets:
  DEV:
    account_identifier: MYORG-DEV
    project_name: PLATFORM.DCM.ANALYTICS_DEV
    project_owner: DCM_DEV_DEPLOYER
    templating_config: DEV
  PROD:
    account_identifier: MYORG-PROD
    project_name: PLATFORM.DCM.ANALYTICS_PROD
    project_owner: DCM_PROD_DEPLOYER
    templating_config: PROD

# a developer sandbox for ticket STORY-1234
snow dcm create PLATFORM.DCM.ANALYTICS_STORY_1234 --target DEV --if-not-exists
snow dcm deploy PLATFORM.DCM.ANALYTICS_STORY_1234 --target DEV --variable "db='STORY_1234'"

# remove the sandbox: drop everything it manages, then the project object
EXECUTE DCM PROJECT PLATFORM.DCM.ANALYTICS_STORY_1234 PURGE;
DROP DCM PROJECT PLATFORM.DCM.ANALYTICS_STORY_1234;

Adopting and handing off objects

  • Adopt existing objects by adding a DEFINE that matches the object's current state. The project owner role must own the object, directly or through a role it inherits. Then run PLAN until it shows no unintended changes. Add the matching GRANT OWNERSHIP so the definitions and the account agree.
  • Transfer ownership safely. If a definition gives a role ownership of an object, also grant that role to the project owner role. PLAN and DEPLOY fail before making changes if the owner role would lose access.
  • Hand off without dropping anything. ALTER <object> ... UNSET DCM PROJECT detaches an object, and ALTER DCM PROJECT ... UNMANAGE GRANT stops tracking a grant. In both cases, remove the definition before the next deploy, or the object or grant is picked up again.
  • Dropping the project object leaves the managed objects in place but unmanaged, and it deletes the deployment history.

Running it in production

  • Use separate owner roles for production and non-production. Grant the production deployment role only to service users. Give it just enough privilege to deploy the project, and authenticate it with OIDC from CI.
  • Give people visibility without deploy rights. READ on the project shows what it manages (SHOW ENTITIES and SHOW GRANTS IN DCM PROJECT). MONITOR adds the full deployment history and artifacts for auditing and debugging. Only the owner can PLAN or DEPLOY.
  • Know where checks stop. PLAN validates that objects can be created. It doesn't run a task's, procedure's, or alert's logic. The sample GitHub workflow's drop check looks only at top-level databases, schemas, tables, and stages, so review the PLAN itself as well.
  • Keep secrets out of definitions. Rendered files and deployment history store external stage definitions in plain text. Put credentials in integrations or secrets that are created outside DCM.
  • Tooling versions: the documented commands need Snowflake CLI 3.24.0 or later. Reusable GitHub Actions (snowflakedb/snowflake-actions/dcm/*) are in preview. On other CI platforms, call the CLI directly.

Strong fit

New projects, platform and environment provisioning, ingestion-layer objects, dynamic-table pipelines, teams that want native plan/deploy with no extra tooling, and teams that like reviewing desired state.

Evaluate carefully

Frequent breaking table changes, heavy data-fix or backfill work, objects or properties not yet supported, strict "revoke anything undeclared" requirements, and teams already productive with an imperative tool.

schemachange

schemachange is an open-source imperative migration tool built for Snowflake. It's community-maintained under Snowflake Labs and isn't an official Snowflake product. It's lightweight: it runs your scripts in order and records what ran. Because it runs any SQL, it can deploy any object that SQL can manage, and since version 4.3.0 it can also run Snowflake CLI steps for code-backed objects.
Script typeNamingBehavior
VersionedV1.2.0__add_orders.sqlRuns once, in version order.
RepeatableR__vw_orders.sqlRe-runs when its checksum changes. Applied after pending versioned scripts. Good for views, functions, and procedures.
AlwaysA__grants.sqlRuns on every deployment.
CLI migrationV1.3.0__deploy_dbt.cli.ymlRuns Snowflake CLI steps (for example snow dbt deploy) as a tracked migration. Works with the V, R, and A prefixes.

  R__vw_orders_enriched.sql

# V1.2.0__deploy_dbt_project.cli.yml

# CI
schemachange deploy --config-folder ./config --dry-run   # on pull request
schemachange deploy --config-folder ./config             # on merge
  • Change history table (default METADATA.SCHEMACHANGE.CHANGE_HISTORY) records every applied script, with checksums. Use one history table for each environment or subject area.
  • Jinja templating for environment-specific names. render shows the final SQL, and verify tests connectivity and config.
  • Out-of-order mode (--out-of-order, 4.3.0+) applies pending versioned scripts even when their version is lower than one already applied. This helps when parallel feature branches merge in any order.
  • Long histories: schemachange has no built-in "baseline" command. Teams manage growth by structuring scripts per release or user story, using repeatable scripts for logic objects, and starting a new history from a cloned environment at a major cut-over when needed.

CLI migration scripts: SQL and code-backed objects in one tool

Before 4.3.0, a typical pipeline had two steps: schemachange for SQL objects, then a separate Snowflake CLI step for dbt projects, Streamlit apps, or Snowpark code. Coordinating the two was custom work. A CLI migration script puts the CLI step inside the migration sequence, so one run deploys both kinds of object in order and records them in the same history.

  • Naming: use the usual V, R, and A prefixes with a .cli.yml extension, or .cli.yml.jinja for templating. CLI and SQL scripts follow the same ordering and run rules, and can be mixed freely.
  • Step fields:
    • cli (required): only snow is supported, and it must be on the PATH.
    • command (required): the CLI command, for example dbt, streamlit, snowpark, or sql.
    • args: the arguments, each as a separate list item.
    • working_dir: resolved relative to the root folder.
    • env and description: optional.
  • Tracking: CLI scripts are recorded in the change history table like SQL scripts. The SCRIPT column holds the full file name, including .cli.yml.
  • Keep connection details out of the file. Use a Jinja variable or a named connection that CI provides, so the same script works in every environment.
migrations/
  V3.1.1__create_analytics_schema.sql
  V3.1.2__deploy_dbt_project.cli.yml.jinja
  V3.1.3__grant_dbt_project_usage.sql

# V3.1.2__deploy_dbt_project.cli.yml.jinja
steps:
  - cli: snow
    command: dbt
    args:                       # one list item per argument
      - "deploy"
      - "my_dbt_project"
      - "--connection"
      - "{{ connection_name }}"
    working_dir: ./dbt
    description: "Deploy dbt project to {{ environment }}"

# wrong: "--connection {{ connection_name }}" as a single item won't work
Versioned or repeatable? A versioned CLI script runs once, so each new release of a dbt project or app needs a new version file. A repeatable script re-runs only when the YAML file itself changes, not when the code it deploys changes. Many teams use a versioned script per release, or call the CLI step on every deploy from an A__ script when redeploying is cheap and safe.

Configuration and authentication

  • Settings come from four places, in this order of precedence: CLI arguments, then environment variables, then schemachange-config.yml, then connections.toml. Keep the YAML file in the repository for project settings, and inject credentials through environment variables in CI.
  • Authentication: use key pair (snowflake_jwt) or OAuth for service users. Programmatic access tokens are accepted in place of a password. connections.toml is convenient for local runs.
  • Traceability: set --query-tag (for example, the release or commit) so every statement can be found in query history.
  • First run: --create-change-history-table creates the history table. The database that will hold it must already exist.
  • Shared logic: put Jinja macros in a --modules-folder. Values passed as secrets are filtered from logs.

Writing scripts that fail safely

  • There are no undo scripts. Fix forward with a new versioned script, and use Time Travel or clones to recover data.
  • Failures are recorded. Since 4.3.0, a failed script is logged in the change history with STATUS = 'Failed'. Alert on that status, and check what the script already applied before you run it again.
  • DDL commits immediately in Snowflake, so a script with several statements can be left half-applied if it fails. Keep each versioned script to one logical change, and write statements that can be re-run safely (IF NOT EXISTS, CREATE OR ALTER).
  • Don't edit a versioned script after it has run. Environments that already applied that version won't run it again. Add a new version instead.
  • Keep repeatable and always scripts idempotent and fast. Avoid DML in repeatable scripts unless running it again is harmless.

Tooling · 06

Flyway & Liquibase

If your team already runs Flyway or Liquibase well on another database, keeping it on Snowflake is often the lowest-risk choice: same review habits, same pipelines, same skills. Both support Snowflake and offer commercial editions with support. Plan a separate path for code-backed objects (see section 9), because these tools run SQL and don't package code.

Flyway (Redgate)

SQL migration files named by version: V2__add_orders.sql for versioned and R__vw_orders.sql for repeatable. Applied versions are recorded in flyway_schema_history. baseline starts tracking an existing database, validate checks that applied scripts haven't changed, and placeholders handle environment names. Snowflake support is a separate module (flyway-database-snowflake). Undo scripts and advanced Snowflake features are paid-edition capabilities.

Liquibase

Changes are changesets in a changelog, written in SQL, YAML, XML, or JSON and identified by author:id. History is stored in DATABASECHANGELOG, with a lock table to prevent concurrent runs. Contexts and labels select changes per environment, update-sql previews the SQL, and changesets can carry their own rollback. Snowflake support is built into the main distribution.

Using them well on Snowflake

  • Write Snowflake-specific objects as plain SQL. Generic change types (Liquibase) and comparison features target common relational objects. Dynamic tables, streams, tasks, stages, and policies are clearer, and safer, as SQL migrations.
  • Expect partial failures. Snowflake commits DDL immediately, so a failed migration can leave part of its changes applied. Flyway records the failed migration and needs a repair after you fix it. With Liquibase, prefer one statement per changeset so failures are small. A run killed mid-way can leave a stale lock, which you clear with release-locks.
  • Keep one history per environment by using a separate schema or database for the history and lock tables in each environment, and give the deployment service user only the privileges it needs.
  • Template names per environment with placeholders (Flyway) or changelog properties (Liquibase), and tie each pipeline stage to one environment configuration.
  • Handle code-backed objects separately. These tools run SQL. They don't upload files, build packages, or deploy dbt projects or Streamlit apps. Add a Snowflake CLI step in the same pipeline (see Code-backed objects).
  • Check licensing before standardizing. Some features shown in demos (undo, drift reports, policy checks, advanced Snowflake script generation) require paid editions. Redgate has announced advanced Snowflake capabilities for Flyway Enterprise in preview.

dbt on Snowflake

dbt is the most common transformation layer on Snowflake. The same project can run in several places. For teams on Snowflake, dbt Projects on Snowflake is the recommended option because it runs dbt natively, with no extra infrastructure, and puts dbt runs, lineage and permissions in the same platform as the data.

Deployment options

dbt Projects on Snowflake Recommended

A DBT PROJECT object in a schema. Snowflake provides the runtime, so you choose the dbt version with DBT_VERSION (dbt Core 1.x or Fusion 2.x), develop in Workspaces, Cortex Code Desktop or a local IDE, and schedule with Tasks.

dbt Core, self-hosted

The open-source CLI (dbt v1, Apache 2.0) run on infrastructure you manage, such as a container, VM, CI runner, or an Airflow worker. It sends SQL to Snowflake.

dbt Fusion engine

dbt Labs' Rust-based engine behind dbt v2, with faster parsing and compilation and built-in SQL analysis. It's an engine, not a hosting option: you can run it inside dbt Projects on Snowflake, locally, self-hosted, or on dbt platform.

dbt platform (formerly dbt Cloud)

dbt Labs' hosted SaaS product: browser IDE, job scheduler, CI jobs, and metadata and semantic-layer services, under a separate dbt Labs subscription. It runs dbt on dbt Labs infrastructure against Snowflake.

Why dbt Projects on Snowflake is the default recommendation

  • No infrastructure to run. No Python environment, runners, or orchestrator cluster, and no version drift across developer machines.
  • Governed by Snowflake RBAC. Runs use the calling role and the profile role, so the run can do only what both roles are allowed to do. MONITOR on the project lets engineers see runs, artifacts, and lineage without granting access to the data.
  • Observability in one place. The DAG, column-level lineage, query history, logs, and traces sit next to the data they describe.
  • Same code, more than one host. Projects stay standard dbt. A dbt_projects_profiles.yml file is read only by Snowflake, so local developers keep their own ~/.dbt/profiles.yml on the same repository.

Typical workflow

# CI on pull request: deploy a test object, then build only what changed
snow dbt deploy my_project_ci --no-auto-compile
# import the last production run's artifacts, then run:
#   build --select state:modified+ --defer --state <imported state>
# (see Snowflake's Slim CI tutorial for the exact import step)

# CD on merge: update the production object
snow dbt deploy my_project --default-target prod
-- Pin the engine, then schedule with a task on a user-managed warehouse
ALTER DBT PROJECT analytics.dbt.my_project SET DBT_VERSION = '1.12.3';

CREATE OR ALTER TASK analytics.dbt.run_daily
  WAREHOUSE = transform_wh          -- serverless tasks can't run dbt projects
  SCHEDULE  = 'USING CRON 0 5 * * * UTC'
AS
  EXECUTE DBT PROJECT analytics.dbt.my_project ARGS = 'build --target prod';

Choosing an engine

  • Start with the latest supported dbt Core 1.x. Snowflake recommends this for most teams because it has the broadest support for Snowflake materializations and packages.
  • Consider Fusion for very large projects (Snowflake's guidance mentions more than 5,000 models), or to get faster parse and compile. Check package compatibility first, and use dbt Labs' dbt-autofix to clear deprecations before switching. Fusion can be tried per project, or for a single run, without changing the account default.

Moving from other deployments

  • From self-hosted dbt Core: add dbt_projects_profiles.yml, deploy with the Snowflake CLI, move schedules to Tasks or have your orchestrator call EXECUTE DBT PROJECT, and retire the runners.
  • From dbt platform: the dbt code moves over, but the platform's own features don't. Replace its scheduler, CI jobs, environment variables, and metadata services with Tasks, CI with the Snowflake CLI, env.yml, and Snowsight lineage. Snowflake's docs note that dbt Cloud projects as such aren't supported, so the project must work on a supported dbt Core or Fusion version.
  • Hybrid is fine during a transition. Some teams keep developing locally or in dbt platform and deploy the same repository to a DBT PROJECT object, which makes metadata and lineage visible in Snowflake. Make sure only one system schedules production runs.

Practices that apply to every deployment

  • dbt manages transformation objects itself. Models create their own tables and views, so don't also define them in DCM or migration scripts. Change-management tools own what dbt doesn't: raw and landing tables, stages, file formats, ingestion tasks, and grants.
  • Replication and ingestion tools behave the same way. Partner replication tools typically create their target tables, run the initial and incremental loads, and handle source schema changes. Leave those landing tables to the tool, and don't also define them in DCM or migration scripts. Your change tool still owns the database, schema, and grants around them.
  • Don't stretch dbt into a change-management tool. Managing procedures, tasks, stages, or grants through hooks and macros is possible, but it's fragile and hard to review. Pair dbt with a change tool instead.
  • Deploy production through CI/CD. Deploying from Workspaces or a Git stage is fine for development objects. Production objects should change only through a reviewed pipeline.
  • Keep warehouses aligned. Use the same warehouse in the task and the profile target so a run doesn't wake two warehouses.
  • Scheduling. Use tags and selectors to run subsets of the graph on different cadences, such as hourly or daily. For event-driven runs, trigger a task from a stream with WHEN SYSTEM$STREAM_HAS_DATA(...), or chain the run after ingestion in a task graph.
  • Python models run in Snowflake through Snowpark. Use them for DataFrame-style logic that would otherwise sit in containers outside the platform.
  • Schema changes dbt can't express, such as reordering or retyping columns on large incremental models, need a coordinated step. Typically that's a migration script or a full refresh.

Terraform

The Snowflake Terraform provider is maintained by Snowflake and covers a large share of objects. It fits best where Snowflake objects connect to cloud resources Terraform already manages (storage and API integrations, PrivateLink-related configuration), and for account-level environment setup.
  • Use it where the team already uses Terraform. Adopting it only for Snowflake brings state files, locking backends, and HCL that teams new to it often struggle with.
  • Draw a clear boundary. Example: Terraform owns integrations, network objects, and environment containers, and the data team's tool owns everything inside the databases. Snowflake's docs advise that each object be managed by only one tool.
  • Be careful with tables. Some resource changes are applied as destroy-and-recreate, which loses the data and history in a table. Prefer to leave data-bearing tables to DCM or an imperative tool. If Terraform does manage tables, review every plan for replacements (-/+) on them, and check whether the resource is a preview feature in your provider version. Preview resources are disabled by default and aren't officially supported.
  • Integrations are a two-way handshake. A storage, API, or notification integration needs values from the cloud provider (such as a role ARN), and the cloud side then needs values Snowflake generates (such as an IAM user or external ID). Terraform can manage both sides in one plan, which is why it fits this layer well.
  • Privileged setup steps. Some account-level configuration needs ACCOUNTADMIN. If a Terraform service user needs it, grant it only for that step through a controlled runbook, then revoke it.

A typical scope

Good fit for Terraform

Storage, API, and notification integrations with their cloud-side IAM; network rules and policies; warehouses and resource monitors; environment databases; account roles and the role hierarchy; service users; and grants at the database and warehouse level.

Usually better elsewhere

Tables and their columns, views, dynamic tables, tasks, procedures, and anything dbt builds. These change often, carry data, or need migration logic. Leave them to DCM, an imperative tool, or dbt.

terraform {
  required_providers {
    snowflake = {
      source  = "snowflakedb/snowflake"
      version = "= 2.x.y"            # pin exactly, upgrade deliberately
    }
  }
  backend "s3" {}                    # remote state with locking
}

resource "snowflake_database" "raw" {
  name = "RAW_${upper(var.env)}"
  lifecycle {
    prevent_destroy = true           # stop a plan from deleting a data-bearing container
  }
}

resource "snowflake_grant_privileges_to_account_role" "loader_raw" {
  account_role_name = "${upper(var.env)}_LOADER"
  privileges        = ["USAGE", "CREATE SCHEMA"]
  on_account_object {
    object_type = "DATABASE"
    object_name = snowflake_database.raw.name
  }
}

Operating it

  • Pin the provider version and upgrade on purpose. Snowflake officially supports only the latest provider version, and minor releases can occasionally change behavior. Read the provider's migration guide before each upgrade, and test it in a non-production workspace first.
  • Treat state as sensitive. Use a remote backend with locking and encryption, limit who can read it, and never commit state or credentials to the repository. Authenticate the service user with key pair or OAuth, not passwords in variables.
  • Use one workspace or state file per environment (or per account) so a mistake in one plan can't touch another environment.
  • Separate privileges with provider aliases. For example, one provider configuration for roles and grants, and another for warehouses and databases. Neither should use ACCOUNTADMIN for routine runs.
  • Import before you manage. Bring existing objects under Terraform with import blocks, then confirm the plan shows no changes before merging.
  • Detect drift. Run a scheduled terraform plan -detailed-exitcode, which exits with code 2 when changes are pending, and alert on it. Changes made by hand show up as diffs, and the next apply reverts them.
  • Don't manage the same grant from two tools. If Terraform and DCM (or scripts) both manage a grant, one tool can revoke what the other expects, and plans keep showing changes. Pick one owner for each grant scope.

Code-backed objects

Some Snowflake objects are defined by files, not only by a DDL statement. They're sometimes called complex or application objects: dbt Projects, notebooks, Streamlit apps, Snowpark code with packages, Snowpark Container Services images, and code bundles. Their DDL contains a pointer (FROM '@stage/...'), not the logic. Deploying them takes three steps:
1. BuildResolve dependencies (dbt deps), package wheels, build images, render config.
2. StageUpload the artifacts to a Snowflake stage or image repository.
3. Create / alterRun the DDL that points at the staged files. Snowflake keeps a versioned copy.

The Snowflake CLI (snow) handles these steps for most object types, for example snow dbt deploy and snow streamlit deploy. Call it directly from CI, from a schemachange .cli.yml migration, or let DCM manage the object types it supports. Use snow, not the older SnowSQL client.

When you can skip build and stage. If nothing needs preparing (no compile, no dbt deps, no generated config), an object can be created straight from a connected Git repository in Snowflake with an ordinary SQL migration. Pin it to a tag such as @my_git_repo/tags/v2.0.0/, not a branch, so every environment deploys exactly the same code.

  • Keep the project directory clean. The CLI processes files in the project directory and can upload them, so don't keep credentials or .env files there.
  • Run plain SQL steps with templating. Use snow sql -f script.sql --enable-templating JINJA --variable "env='PROD'" for post-deployment steps, such as SQL that a declarative tool doesn't manage. Remember these steps have no history of their own, so make them idempotent.
  • Pin the CLI version in CI and authenticate with OIDC or key pair. Features such as DCM commands need a minimum CLI version.

CI/CD pipeline

Stages

Pull requestLint, unit-test, then plan or dry-run against the target environment. Post the output for reviewers.
Merge to mainDeploy to dev/test with that environment's service user. Run dbt build and tests.
ReleasePromote the same commit to production after approval. Only configuration changes between environments.
VerifyRun smoke tests, data quality expectations, and row-count and key checks. Alert on failure.

Order within a deployment

  1. Object state (DCM deploy or migration scripts): schemas, raw tables, stages, grants.
  2. Code-backed objects (Snowflake CLI): dbt project, procedures, apps.
  3. Transformation run or refresh (dbt build, dynamic table refresh) where required.
  4. Post-deploy validation.

Practices that matter

  • Authentication: workload identity federation (OIDC) from your CI platform, or key-pair auth, with a separate service user and role for each environment. No long-lived passwords. Snowflake publishes CLI integrations for GitHub Actions (GA), GitLab CI/CD, and Azure DevOps (preview).
  • Branching: trunk-based development with short-lived feature branches, plus release branches or tags that gate production on a regular cadence. Data pipelines rarely suit true continuous deployment because integration tests against real data take time.
  • Environments: seed dev and test with zero-copy clones of production instead of replaying DDL. Rebuilding from scripts gives you empty tables.
  • Serialize deployments to each environment so two pipelines can't apply changes at the same time.
  • Breaking changes: use expand, then migrate, then contract: add the new column or table, backfill, switch consumers, and drop the old one in a later release.

Access & RBAC

  • SCIM handles who; Snowflake grants handle what. With Okta or Entra ID SCIM, the identity provider creates users and roles that match groups, pushed one way from the IdP. Those roles start with no privileges. You manage role hierarchy and grants inside Snowflake, in code. Don't hand-edit or drop SCIM-owned users and roles in Snowflake, because it breaks the sync.
  • Scope what SCIM pushes. Sync only the groups meant for Snowflake, for example from a dedicated group or organizational unit, not the whole directory. Long-lived directories carry many groups that shouldn't become Snowflake roles.
  • Keep grants in code. Options include DCM GRANT statements, migration scripts (often repeatable or always scripts), Terraform owned by the platform team, or a dedicated permissions tool. Reliably revoking privileges that were granted outside the tool is still a gap in most tooling. If you need it, schedule a check that compares SHOW GRANTS with the declared model.
  • Declare permissions above the level of single GRANTs. Written one at a time, grants spread across many files at one-role, one-privilege, one-object granularity, which makes them hard to audit. Two patterns help:
    • Rules-based definition: describe access at a higher level (for example, "role X reads everything in schema Y") in a YAML or JSON file, and use a tool or script to expand it into GRANT and REVOKE statements. Permifrost is a concrete open-source option for this pattern (see below).
    • Permission matrix: keep a role-by-object privilege matrix under version control, load it into a Snowflake table in the pipeline, and run a stored procedure that applies it. The procedure can also revoke privileges that aren't in the matrix, which closes the revoke gap above.
  • Functional and access roles. Grant object privileges to access roles (database roles work well), grant access roles to functional or persona roles, and give users only functional roles. Use a dedicated owner role for each environment so ownership doesn't drift to individuals.
  • Secondary roles. New users default to DEFAULT_SECONDARY_ROLES = ('ALL'). If you want users to switch roles explicitly (for example, people who work across separate legal entities), block secondary roles with a session policy (ALLOWED_SECONDARY_ROLES = ()) at the account or user level, or set the user property to (). CREATE statements are always authorized by the primary role only. Reference.
CREATE SESSION POLICY governance.policies.no_secondary_roles
  ALLOWED_SECONDARY_ROLES = ();
ALTER ACCOUNT SET SESSION POLICY governance.policies.no_secondary_roles;

Permifrost: permissions as code

Permifrost is an open-source Python tool, maintained by the GitLab Data Team, that manages Snowflake permissions declaratively through a YAML spec file. It compares the spec to the current account state and generates (or executes) the GRANT and REVOKE commands needed to converge. Because the spec is the single source of truth, any privilege not declared in it is revoked—which closes the revoke gap described above.

Strengths

  • Declarative: one YAML file defines the entire permission model, version-controlled in Git.
  • Revokes undeclared grants automatically, preventing privilege creep.
  • --dry mode generates SQL for review without applying it, fitting naturally into a PR-based workflow.
  • Abstracts Snowflake grants into read/write, reducing boilerplate.
  • Supports key-pair, OAuth, and external-browser authentication.
  • Spec files support !include for splitting large configurations by team or domain.

Trade-offs

  • Community-maintained (v0.15.x), not an official Snowflake product.
  • Requires the SECURITYADMIN role; fails with any other role.
  • Covers roles, users, warehouses, integrations, and database/schema/table grants only. Dynamic tables, tasks, stages, policies, and other object types are out of scope.
  • The read/write abstraction doesn't map to every Snowflake privilege (for example, CREATE DYNAMIC TABLE or policy grants).
  • Does not revoke object ownership or warehouse privileges.
  • All entity names in the spec must be lowercase.

Example spec

# permifrost.yml
databases:
  - analytics:
      shared: false
  - raw:
      shared: false

roles:
  - analyst_role:
      warehouses:
        - query_wh
      member_of:
        - sysadmin
      privileges:
        databases:
          read:
            - analytics
            - raw
        schemas:
          read:
            - analytics.*
            - raw.*
        tables:
          read:
            - analytics.*.*
            - raw.ingest.*

  - loader_role:
      warehouses:
        - load_wh
      privileges:
        databases:
          read:
            - raw
          write:
            - raw
        schemas:
          read:
            - raw.*
          write:
            - raw.ingest
        tables:
          write:
            - raw.ingest.*

users:
  - analyst_user:
      can_login: true
      member_of:
        - analyst_role
  - loader_svc:
      can_login: true
      member_of:
        - loader_role

warehouses:
  - query_wh:
      size: x-small
  - load_wh:
      size: small

Running in CI

# Pull request: preview changes
permifrost run permifrost.yml --dry

# Merge to main: apply
permifrost run permifrost.yml
Pair it with your change tool. Permifrost owns grants and role memberships. It does not create databases, schemas, or tables. Use DCM Projects, schemachange, Terraform, or another tool to manage the objects themselves, and Permifrost to manage who can access them. As with any tool combination, make sure grant ownership doesn't overlap: if DCM or Terraform also manages grants, choose one owner per grant scope.

Account strategy

Start with one account

Snowflake accounts scale well, and warehouses and databases are isolated from each other. A single account with dev, test, and prod databases plus RBAC is simplest. Zero-copy cloning to refresh pre-production only works within an account.

Use multiple accounts for real boundaries

Separate legal entities, regulatory isolation, distinct security postures, or data residency. Put each entity's environments inside its own account so cloning still works, and use read-only data sharing for cross-entity access.

Environments in one account vs separate accounts

Many environments per accountOne environment per account
SeedingCREATE DATABASE ... CLONE copies objects and data in one fast step.No cross-account cloning. Share data from production and copy it with CREATE TABLE ... AS SELECT, and deploy all other objects with your change tool. Slower, and it needs automation.
Release and behavior-change testingEvery environment gets new releases at the same time.A pre-production Enterprise (or higher) account can be designated for early access to new releases (typically at least 48 hours ahead). Behavior-change bundles can be enabled there first.
Object namingAccount-level objects need an environment prefix or suffix, and tools must parameterize names.Names can match across environments. Tools still need per-environment targets.

CostOne edition and credit price for all environments.Pre-production can run on a different edition. Check sharing restrictions between Business Critical and lower editions first.

Creating a new environment

1. BuildCreate the container: a cloned database in the same account, or a new account.
2. SeedClone from production, or share plus CTAS across accounts. Deploy account-level and non-table objects with your change tool.
3. ProtectRemove or mask sensitive data according to your security policies, and apply policies to every object.
4. GrantGrant access to the team's roles, then start using it.
Clones keep their references. Views, procedures, functions, and tasks inside a clone can still point at objects outside it, including production, if they use fully qualified names. Use environment variables or templating in definitions, and redeploy those objects with your change tool after cloning.
  • With multiple accounts, every account needs its own network setup (for example PrivateLink), SCIM integration, roles, and policies. Manage these from one codebase with per-account targets so they stay in sync.
  • Shared data is read-only for consumers. Changes happen in the source account and flow through the share.
  • Plan replication and failover to a second region early if business continuity is a requirement.
  • Fix naming conventions before the first object is created. For example: <DOMAIN>_<ENV> databases with medallion or layer schemas, and environment-suffixed roles and warehouses.

Field patterns

Two anonymized examples of how customer teams applied these ideas.

Pattern A: Greenfield data-product team

Context: A central platform team provisions a "project container" for each product team: dev, test, and prod databases, medallion schemas, roles, and warehouses, defined in Terraform. One team of about five developers is building an AI-assisted master-data product with Cortex functions and agents.

Journey: They started with native declarative definitions for ingestion objects and dbt for transformations. As the product changed quickly, they hit frequent breaking table changes and data fixes, and their objects ended up split across three tools with no clear owner. They proved out converting their definitions to versioned migration scripts.

Decisions: Terraform stays at the platform layer. Inside each project they use one imperative tool for object state (with CLI steps for containers and apps), dbt for transformation, native Tasks for orchestration, GitLab CI for deployment, and a release-branch cadence.

Lessons: Settle object ownership before the object count grows. Give AI coding agents read-only metadata access, not only the repo. Write down the central-team / project-team boundary so other teams can reuse the template.

Pattern B: Regulated warehouse migration

Context: A financial-services company with separate brokerage and banking entities is migrating a decade-old cloud warehouse to Snowflake under a fixed contract deadline. Some pipelines feed regulatory and customer-facing outputs and must be re-certified.

Decisions:

  • Keep the imperative tool the team already knows (Liquibase) for database objects.
  • Keep dbt Core with self-hosted Airflow, and also deploy the dbt project object to Snowflake for its metadata.
  • Limit Terraform to infrastructure-team objects (network, connectors).
  • Use one account per legal entity, each with its own environments, and read-only shares across entities.
  • Block secondary roles so people who wear several hats switch roles explicitly.

Migration safeguards: Move critical jobs one-for-one into a restricted database that only service users can read, so consumers don't build on legacy logic. Deprecate unused models instead of lifting and shifting everything. Run old and new systems in parallel and log automated comparisons (row counts, key statistics) to a table for leadership sign-off and audit evidence.

Open items they planned for: how grants are managed across accounts, a deployment path for future Streamlit and Snowpark objects, and a runbook for privileged network setup.
