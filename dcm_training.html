Section 1 · 0-4 min

Why DCM

Most Snowflake estates start the same way: worksheets, hand-run DDL, a "prod fix" nobody wrote down. Environments drift apart, deployments depend on a person, and nobody can answer "what changed on Tuesday?". Imperative migration scripts help, but the current shape of an object is spread across years of files.

DCM Projects is Snowflake's native, declarative change management (GA in August 2026). You describe the state you want; Snowflake computes the diff, orders it, and applies it. Snowflake's DevOps guidance positions it as the recommended native option for objects inside your databases, alongside Terraform for account and cloud infrastructure.

Move faster

One readable file per area, Jinja for environments, Cortex Code to author and debug definitions.

Deploy predictably

PLAN shows every CREATE, ALTER and DROP before anything changes. The same files go to every environment.

Stay traceable

Every deployment is numbered, can carry an alias, and keeps its rendered definitions as artifacts.

Recover quickly

Re-apply the defined state to remove drift, or redeploy a previous deployment's definitions.

The principles we will apply

  1. Everything in Git. Production gets nothing that didn't come through version control.
  2. Deploy only through CI/CD, with service users. People touch production as little as possible.
  3. Convergent state. DEV, QA and PRD differ only by configuration, never by hand-applied fixes.
  4. Validate before deploy. Every pull request shows a PLAN; drops get special attention.
  5. Roll forward. Fix a bad change with a new change. Restoring definitions does not restore data.
  6. One owner per object. Two tools reconciling the same object will fight each other.

Concepts

Where DCM sits: the layers model

LayerExamplesTypical owner / tool
IdentityUsers, groupsIdentity provider through SCIM
Account & environmentDatabases, warehouses, roles, network policiesPlatform team: DCM Projects or Terraform
Database objectsSchemas, tables, views, dynamic tables, tasks, stages, functions, procedures, grants, expectationsDCM Projects (or an imperative tool)
TransformationModels that build tables from sourcesdbt (dbt Projects on Snowflake), or dynamic tables in DCM
Code-backed objectsdbt project objects, Streamlit, notebooks, packaged Snowpark codeSnowflake CLI from the pipeline
Data fixes & backfillsUPDATE, data moves, renames with dataA tracked imperative path, never the definition files
Build an object-ownership map first. List each object type, give it exactly one owner, keep the list in the repo. It drives tool choice more than features do. DCM does not manage users, SSO, account creation, or catalog, notification and security integrations.

Declarative vs imperative

Declarative (DCM, Terraform)Imperative (schemachange, Flyway, Liquibase)
You writeWhat the object should look likeOrdered scripts with the exact changes
StrengthsOne readable definition; plan and diff; drift detectionAny change, including backfills and renames
Watch outRemoving a definition drops the object; renames need a separate stepNo single "current state"; scripts must be idempotent

A diff tool sees before and after, not intent. Moving a column's data into a new table looks like "create table, drop column" and the data is lost. Use expand, migrate, contract: add the new structure (DCM), backfill with a tracked script, switch consumers, then remove the old definition in a later release.

The building blocks

DCM project object

A schema-level object (CREATE DCM PROJECT) that stores deployment history and tracks what it manages. Its owner role is the only role that can PLAN or DEPLOY.

manifest.yml

Targets (account, project object, owner role, configuration) plus templating defaults and per-configuration overrides.

Definition files

sources/definitions/*.sql holding DEFINE, GRANT and ATTACH statements, with Jinja variables, loops and macros.

Deployment

Each DEPLOY gets a number (DEPLOYMENT$n) and an optional alias. Think of the alias as the commit message for the environment.

DEFINE = CREATE OR ALTER, plus "remove means drop"

-- sources/definitions/raw.sql
DEFINE TABLE ORDERS{{env_suffix}}.RAW.ORDERS (
    ORDER_ID NUMBER NOT NULL, CUSTOMER_ID NUMBER NOT NULL,
    ORDER_TS TIMESTAMP_NTZ, AMOUNT NUMBER(12,2), STATUS VARCHAR(20)
)
CHANGE_TRACKING = TRUE
DATA_METRIC_SCHEDULE = 'TRIGGER_ON_CHANGES';

GRANT SELECT ON TABLE ORDERS{{env_suffix}}.RAW.ORDERS TO DATABASE ROLE ORDERS{{env_suffix}}.RAW_READER;

ATTACH DATA METRIC FUNCTION SNOWFLAKE.CORE.NULL_COUNT
    TO TABLE ORDERS{{env_suffix}}.RAW.ORDERS ON (ORDER_ID)
    EXPECTATION NO_NULL_ORDER_IDS (value = 0);
  • Use fully qualified names everywhere. DCM works out dependency order for you.
  • Only changes that CREATE OR ALTER supports can be deployed. Some properties are immutable (for example a pipe's COPY body), which means drop and recreate.
  • A project can never DEFINE its own parent database or schema. The project object lives in a separate container (here DCM_TRAINING.PROJECTS).

The lifecycle

PLAN renders Jinja, compares definitions with the account, converts them into CREATE, ALTER, DROP, GRANT and REVOKE statements, sorts them by dependency, compiles them and checks privileges. DEPLOY runs that same pipeline again and then executes it. DEPLOY recomputes the changeset; it does not replay a saved PLAN.

Section 3 · 11-16 min

Environment strategy

Rule 1: one project object per environment

A DCM project has exactly one deployed instance. Deploying a different configuration to the same project drops everything that configuration doesn't define. So DEV, QA and PRD each get their own project object. All three point at the same files and differ only in configuration.

Rule 2: template every account-level name

Databases, warehouses and account roles get {{env_suffix}}. Two projects can't manage the same object, so un-templated names collide as soon as a second environment or developer deploys.

# manifest.yml (excerpt)
targets:
  DEV: { project_name: DCM_TRAINING.PROJECTS.ORDERS_DEV, project_owner: DCM_DEVELOPER,     templating_config: DEV }
  QA:  { project_name: DCM_TRAINING.PROJECTS.ORDERS_QA,  project_owner: DCM_QA_DEPLOYER,   templating_config: QA }
  PRD: { project_name: DCM_TRAINING.PROJECTS.ORDERS_PRD, project_owner: DCM_PROD_DEPLOYER, templating_config: PRD }
templating:
  defaults:
    env_suffix: '_DEV'
    wh_size: 'XSMALL'
    task_state: 'SUSPENDED'
    teams: [ { name: 'FINANCE', raw_access: true }, { name: 'MARKETING', raw_access: false } ]
  configurations:
    QA:  { env_suffix: '_QA',  project_owner_role: 'DCM_QA_DEPLOYER' }
    PRD: { env_suffix: '_PRD', project_owner_role: 'DCM_PROD_DEPLOYER', wh_size: 'SMALL', task_state: 'STARTED' }

Variables resolve in three tiers: defaults, then the configuration, then runtime values (USING CONFIGURATION DEV (env_suffix => '_SBX_42') or --variable).

Rule 3: separate owner roles, least visibility for everyone else

DCM_DEVELOPER

Owns DEV and per-ticket sandboxes. Developers have it.

DCM_QA_DEPLOYER / DCM_PROD_DEPLOYER

Own QA and PRD. In real life they are granted only to CI service users that authenticate with OIDC or key pair.

DCM_AUDITOR

READ shows what a project manages. MONITOR adds full deployment history and artifacts. Neither can deploy. Watch secondary roles: a user who also holds a deployer role can still deploy from an auditor session.

Keep the owner in control. Roles that the project creates are granted to {{project_owner_role}}. If a definition transfers OWNERSHIP to a role, the owner role must hold that role. Otherwise PLAN and DEPLOY refuse to run rather than lock the owner out.

Rule 4: sandbox per ticket, and pick a project shape

  • Sandbox: a separate project object and a unique suffix (ORDERS_SBX_STORY_1234). Use PLAN DELTA while editing, a full PLAN before deploying, and PURGE plus DROP when the ticket closes.
  • A. One folder, one target: most objects share an owner. Keep loops modest; about 20 iterations is a good rule of thumb.
  • B. One folder, many targets: same definitions, but different owners or independent deploys (DEV/QA/PRD, or one target per tenant).
  • C. Separate folders: a platform project (databases, warehouses, admin roles) and domain projects that build inside them. Keep dependencies one-directional and deploy upstream first; DCM does not coordinate across projects.

Starting with one account is simplest: zero-copy cloning only works within an account. Use several accounts for real boundaries (legal entities, regulation, residency). The manifest then just changes account_identifier per target.

1

Bootstrap ~3 min · ACCOUNTADMIN, once

The platform team's part: a container for project objects, a source stage, one deployer role per environment plus an auditor, and the three project objects. Each one is created by its own deployer role, so that role owns it.

CREATE ROLE IF NOT EXISTS DCM_PROD_DEPLOYER;
GRANT CREATE DATABASE, CREATE WAREHOUSE, CREATE ROLE, EXECUTE TASK, EXECUTE DATA METRIC FUNCTION
    ON ACCOUNT TO ROLE DCM_PROD_DEPLOYER;
GRANT CREATE DCM PROJECT ON SCHEMA DCM_TRAINING.PROJECTS TO ROLE DCM_PROD_DEPLOYER;
USE ROLE DCM_PROD_DEPLOYER;
CREATE DCM PROJECT IF NOT EXISTS DCM_TRAINING.PROJECTS.ORDERS_PRD;
GRANT READ, MONITOR ON DCM PROJECT DCM_TRAINING.PROJECTS.ORDERS_PRD TO ROLE DCM_AUDITOR;

All of this runs once, before the session: setup_training.sh sets your account in the manifests and runs dcm_training_setup.sql. That script also uploads both releases to @DCM_TRAINING.PROJECTS.SOURCES/release-1.0/ and /release-1.1/. In the lab, just open it and explain it. In a real project, the source would be a Git repository clone or a Snowsight Workspace path (snow://workspace/...).

2

First DEV deployment ~4 min

USE ROLE DCM_DEVELOPER;
EXECUTE DCM PROJECT DCM_TRAINING.PROJECTS.ORDERS_DEV
    PLAN USING CONFIGURATION DEV
    FROM '@DCM_TRAINING.PROJECTS.SOURCES/release-1.0/';          -- review: all CREATE

EXECUTE DCM PROJECT DCM_TRAINING.PROJECTS.ORDERS_DEV
    DEPLOY AS "release-1.0" USING CONFIGURATION DEV
    FROM '@DCM_TRAINING.PROJECTS.SOURCES/release-1.0/';

-- run PLAN again: "changeset": []  <- convergent and idempotent
EXECUTE TASK ORDERS_DEV.RAW.TSK_LOAD_SAMPLE_ORDERS;              -- task is SUSPENDED in DEV; run once
CALL SYSTEM$WAIT(20);                                               -- EXECUTE TASK is asynchronous
EXECUTE DCM PROJECT DCM_TRAINING.PROJECTS.ORDERS_DEV TEST ALL;   -- PREVIEW feature

Things to point out: the warehouse was created before the dynamic table that uses it, although nobody ordered the files. The teams loop produced ORDERS_FINANCE_DEV (with RAW access) and ORDERS_MARKETING_DEV (without). SHOW ENTITIES IN DCM PROJECT lists everything that is now managed.

3

Feature change: release 1.1 ~3 min

The feature branch adds a CHANNEL column, a V_REVENUE_BY_CHANNEL view and its grant, and changes the task body. Compare orders_project_1-0 with orders_project_1-1: a small diff in four files.

EXECUTE DCM PROJECT ...ORDERS_DEV PLAN DELTA USING CONFIGURATION DEV FROM '.../release-1.1/';  -- fast inner loop
EXECUTE DCM PROJECT ...ORDERS_DEV PLAN       USING CONFIGURATION DEV FROM '.../release-1.1/';  -- the real gate

-- read the changeset as rows
SELECT c.value:type::STRING, c.value:object_id:domain::STRING, c.value:object_id:fqn::STRING
FROM TABLE(RESULT_SCAN(LAST_QUERY_ID())) r, LATERAL FLATTEN(INPUT => r.$1:changeset) c;
-- expect 5: ALTER TABLE (column added), CREATE VIEW, ALTER TASK, ALTER DATABASE ROLE (grant), ALTER ROLE (ownership)

EXECUTE DCM PROJECT ...ORDERS_DEV DEPLOY AS "feature-channel" USING CONFIGURATION DEV FROM '.../release-1.1/';
PLAN DELTA is not a gate. It skips unchanged definitions, so it can't see what someone changed by hand. Always run a full PLAN before DEPLOY.
4

Promote: QA, then PRD ~5 min

Same files, different project and configuration. This is exactly what CI runs on merge.

USE ROLE DCM_QA_DEPLOYER;
EXECUTE DCM PROJECT ...ORDERS_QA PLAN USING CONFIGURATION QA FROM '.../release-1.1/';
EXECUTE DCM PROJECT ...ORDERS_QA DEPLOY AS "release-1.1" USING CONFIGURATION QA FROM '.../release-1.1/';

-- QA gate: TEST ALL (PREVIEW) or a GA SQL smoke test that returns PASS / FAIL
SELECT IFF(COUNT(*) > 0 AND COUNT_IF(ORDER_ID IS NULL) = 0
           AND COUNT(*) = COUNT(DISTINCT ORDER_ID) AND MIN(AMOUNT) >= 0, 'PASS', 'FAIL')
FROM ORDERS_QA.RAW.ORDERS;

USE ROLE DCM_PROD_DEPLOYER;
EXECUTE DCM PROJECT ...ORDERS_PRD PLAN USING CONFIGURATION PRD FROM '.../release-1.1/';
-- drop protection: this must return zero rows
SELECT ... WHERE c.value:type::STRING = 'DROP'
  AND c.value:object_id:domain::STRING IN ('DATABASE','SCHEMA','TABLE','STAGE','DYNAMIC_TABLE');
EXECUTE DCM PROJECT ...ORDERS_PRD DEPLOY AS "release-1.1" USING CONFIGURATION PRD FROM '.../release-1.1/';

In PRD the task is declared STARTED. Target state is reasserted on every deploy, so a hand-run ALTER TASK ... SUSPEND lasts only until the next release. To pause a task, change its definition. Without a declared state, a new task is created suspended.

Same step from the CLI (see dcm_training_cli.sh), run in orders_project_1-1/:
snow dcm plan --target QA --role DCM_QA_DEPLOYER --save-output, then snow dcm deploy --target QA --role DCM_QA_DEPLOYER --alias "release-1.1", then the same for --target PRD --role DCM_PROD_DEPLOYER, with the jq drop check on out/plan_result.json in between. Always pass --role: the CLI runs as the connection's role, not the manifest's project_owner.
5

Drift, co-existing grants, recovery and audit ~4 min

-- a "quick fix" by hand
ALTER WAREHOUSE ORDERS_WH_DEV SET AUTO_SUSPEND = 600;
GRANT SELECT ON VIEW ORDERS_DEV.SERVE.V_DAILY_REVENUE TO ROLE PUBLIC;

EXECUTE DCM PROJECT ...ORDERS_DEV PLAN ... ;                         -- warehouse drift: 600 -> 60
EXECUTE DCM PROJECT ...ORDERS_DEV DEPLOY AS "drift-fix" FROM DEPLOYMENT "feature-channel";
SHOW GRANTS ON VIEW ORDERS_DEV.SERVE.V_DAILY_REVENUE;                  -- the PUBLIC grant survived!

EXECUTE DCM PROJECT ...ORDERS_DEV PLAN FROM DEPLOYMENT "release-1.0";  -- shape restore: drops CHANNEL + view

USE ROLE DCM_AUDITOR;
USE SECONDARY ROLES NONE;     -- otherwise held deployer roles still apply
SHOW DEPLOYMENTS IN DCM PROJECT DCM_TRAINING.PROJECTS.ORDERS_PRD;
SELECT * FROM TABLE(DCM_TRAINING.INFORMATION_SCHEMA.DCM_DEPLOYMENT_HISTORY(
    PROJECT_NAME => 'DCM_TRAINING.PROJECTS.ORDERS_DEV'));

Drift is reverted

Properties of managed objects converge back to the definition on the next deploy. A scheduled full PLAN is a cheap drift detector.

Extra grants co-exist

DCM manages the grants it deployed. Grants made outside it are neither shown nor revoked. To enforce "no undeclared privileges", add a scheduled SHOW GRANTS comparison or a dedicated permissions tool.

Restore shape, not data

FROM DEPLOYMENT re-applies old definitions. Data in a dropped column is gone. In PRD, prefer rolling forward, and use Time Travel or clones for data.

6

Optional patterns and cleanup ~1 min, read along

  • Sandbox per ticket: USING CONFIGURATION SANDBOX (env_suffix => '_SBX_STORY_1234') on its own project object.
  • Seed pre-production from PRD: CREATE DATABASE ... CLONE ORDERS_PRD. Clones keep fully qualified references, so redeploy the templated objects afterwards.
  • Hand off without dropping: ALTER <object> ... UNSET DCM PROJECT or ALTER DCM PROJECT ... UNMANAGE GRANT, then remove the definition before the next deploy.
  • Cleanup: PURGE drops every managed object and its data, so use it only on DEV and sandboxes. DROP DCM PROJECT alone leaves objects in place, unmanaged, and deletes the history. Both are commented out in the companion.
Section 5 · 34-38 min

CI/CD and running it in production

Reference pipeline

# .github/workflows/dcm.yml (excerpt) - dcm/* actions are PREVIEW; the PRD job uses plain snow CLI
deploy-prd:
  needs: deploy-qa
  environment: PRD                 # required reviewers = approval gate
  concurrency: dcm-deploy-PRD      # never two deploys to one environment at once
  steps:
    - uses: snowflakedb/snowflake-cli-action@v2
      with: { use-oidc: true, cli-version: "3.31.0" }
    - run: snow dcm plan --target PRD --save-output
    - run: test $(jq '[.changeset[]|select(.type=="DROP" and (.object_id.domain|IN("DATABASE","SCHEMA","TABLE","STAGE","DYNAMIC_TABLE")))]|length' out/plan_result.json) -eq 0
    - run: snow dcm deploy --target PRD --alias "release-${{ github.sha }}"
    - run: snow dcm refresh --target PRD && snow dcm test --target PRD
  • Authentication: OIDC workload identity federation or key pair, with one service user and role per environment. No long-lived passwords; GitHub stores only the user name.
  • Branching: trunk-based with short-lived feature branches. Promote the same commit to PRD; only configuration changes.
  • Order inside a release: object state (DCM), then code-backed objects (CLI), then refresh or transform, then validate.
  • Know where checks stop: PLAN proves objects can be created, but it doesn't run task, procedure or alert logic. The sample drop check covers only top-level data objects, so humans still read the PLAN on the PR.

Production gotchas

BehaviorWhat to do
Removing a DEFINE drops the object on the next deployMake PLAN review (especially DROP) a required PR check
Partial deploys: DDL commits as it goesFix the cause and deploy again; DCM converges to the defined state
Renames, some column type changes, immutable propertiesDo them outside DCM (or drop and recreate), then update the definition until PLAN is empty
Grants created outside DCM are not revokedScheduled SHOW GRANTS comparison, or a dedicated permissions tool
New tasks and alerts deploy suspended; STARTED is reasserted each deployDeclare the state per environment, as this lab does
Rendered definitions and history are stored as plain textNo secrets in definitions; use integrations or secrets created outside DCM
Dropping the project object deletes deployment historyLock DROP DCM PROJECT behind the owner role; audit with MONITOR

Adopting what already exists

Run GET_DDL, change CREATE to DEFINE, template the names, and re-run PLAN until it shows zero changes for the adopted objects. Then deploy to take them under management. The project owner role must own the objects, directly or through role inheritance. Snowflake Labs publishes migration tooling to speed this up, and Cortex Code's DCM skill automates the loop.

Anti-patterns

Two tools, one object

DCM and Terraform (or dbt hooks) both changing a warehouse means endless drift. Give each object one owner.

"Git connected" = DevOps

A Git repository in Snowflake gives you no approvals, ordered environments or gates. Run deployments from CI.

EXECUTE IMMEDIATE FROM loops

No history, no run-once guarantee, no plan. Keep it for ad-hoc scripts.

One project, many configs

Deploying QA config into the DEV project drops DEV-only objects. Use one project per environment.

Choosing the combination

SituationSensible starting point
New to change management, mostly supported objects, wants native toolingDCM Projects + dbt Projects + Tasks, plus a tracked script path for data fixes
Frequent breaking table changes, backfills, renamesschemachange (with CLI steps) + dbt
Team already fluent in Flyway or LiquibaseKeep it for database objects, plus Snowflake CLI for code-backed objects
Infra team runs Terraform for the cloudTerraform for integrations, network and account containers; DCM inside databases
Mostly dynamic tables and simple pipelinesDCM end to end: dynamic tables, tasks, expectations
Must revoke every undeclared privilegeA dedicated permissions tool (for example Permifrost) for grants, any tool for objects
Section 6 · 38-40 min

Recap

Production readiness checklist

  1. Ownership map written: what DCM owns, what dbt, Terraform and the IdP own.
  2. One project object and one owner role per environment; PRD owner granted only to a CI service user.
  3. All account-level names templated; configuration is the only difference between environments.
  4. PR runs a full PLAN; drops are reviewed and machine-checked; PRD requires approval.
  5. Deployments are serialized per environment and always carry an alias (commit SHA or release).
  6. Post-deploy verification: expectations (TEST, preview) or GA smoke queries.
  7. Scheduled full PLAN for drift; scheduled grant comparison if undeclared privileges matter.
  8. Breaking changes use expand, migrate, contract; data fixes go through a tracked imperative path.
  9. Auditors get READ and MONITOR, not ownership.
